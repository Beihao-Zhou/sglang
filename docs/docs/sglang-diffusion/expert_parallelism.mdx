Expert parallelism (EP) shards the experts of a MoE DiT across GPUs instead of
replicating them on every rank. On a 128-expert model the expert weights are the
overwhelming majority of the parameters, so replicating them is what forces a
large MoE DiT into CPU offload — or out of memory entirely.

EP is enabled with `--ep-size`, and currently applies to the LingBot-Video MoE
DiT.

```bash
# Experts sharded 4-way, sequence split 2-way (Ulysses), orthogonally.
sglang generate --model-path <lingbot-video-moe> \
  --num-gpus 8 --ep-size 4 --ulysses-degree 2 \
  --prompt "..." --save-output
```

## EP is its own parallel axis

EP is a first-class, orthogonal parallel dimension:

```
num_gpus = dp_size × cfg_parallel_degree × tp_size × ep_size × sp_degree
```

`ep_size` composes with tensor and sequence parallelism instead of borrowing
their ranks. `--num-gpus 8 --tp-size 2 --ep-size 4` is a genuine 2×4 mesh
(attention sharded 2-way by TP, experts sharded 4-way by EP), mirroring srt's
`moe_tp × moe_ep` model. This is what lets the target video layout — **sequence
parallelism for attention + expert parallelism for the FFN** — run at once,
rather than spending the GPU budget on TP and losing SP.

Each rank computes the partial output of only the experts it owns, and a single
all-reduce over the EP group re-forms the dense result. That is valid because the
ranks in an EP group hold the *same tokens*: EP is orthogonal to SP, so an EP
group shares one sequence slice (and one CFG branch and one TP shard), and the
router therefore makes identical decisions across it.

<Note>
This "replicated-token" design still streams every token through every rank in
the EP group. Removing that — routing each token only to its expert's rank via
all-to-all **dispatch** — is the next step, and is what will let experts shard
across ranks that hold *different* tokens.
</Note>

Because EP is its own axis it consumes its own GPUs and enters the `num_gpus`
product above. The expert count must be divisible by `ep_size`.

## What it buys

Measured on 2×H100 80GB, LingBot-Video MoE 30B, 640×384, 17 frames, 12 steps,
identical seed and prompt, with `ep_size` as the only variable (these numbers
predate the orthogonal-axis change and were taken on the earlier TP-coupled EP
arrangement; the memory trend — per-rank expert VRAM ÷ `ep_size` — is unchanged):

| | `--ep-size 1` | `--ep-size 2` | `--ep-size 2` + FSDP |
| --- | --- | --- | --- |
| VRAM per GPU (after load) | 74.4 GB | 31.5 GB | sharded |
| VRAM per GPU (denoise peak) | 74.4 GB | 42.0 GB | — |
| Denoise per step | 1.81 s / 1.64 s | 1.39 s / 1.11 s | — |
| Total pixel-generation time | 63.7 s | 31.5 s | 8.5 s |

Two runs of each configuration are shown for per-step time because wall-clock
varies with filesystem cache warmth; the ordering is stable across pairings.

The dense configuration only fits at all because the auto-tuner turns on DiT CPU
offload. That is the real cost EP removes: halving the resident expert weights
also halves the per-block host-to-device streaming traffic, so EP more than pays
back the all-reduce it adds. With FSDP, EP removes the need for offload entirely.

## Numerical behavior: EP is bit-exact to dense

<Note>
EP reproduces the dense (non-EP) output **bit-for-bit**, at every `ep_size`. A
fixed seed gives the same sample with or without EP; `ep_size` is not part of the
sampling configuration.
</Note>

This required care, because the naive split is *not* bit-exact — the story below
records why, and how the fp32 partial-output mode closes it.

**The expert computation was already bitwise exact.** Comparing the unreduced
per-expert outputs (`no_combine`) of an EP-sharded run against the dense run gives
a *bitwise identical* result. The contiguous expert partition, the non-local-expert
filtering, and the weight slicing contribute exactly zero error. Only the combine's
rounding was ever the issue.

**The naive bf16 split double-rounds.** For a token routed to 8 experts, the dense
path accumulates all eight contributions in fp32 and rounds once:

```text
dense:  out = bf16(c1 + c2 + ... + c8)                      # 1 rounding
EP-2:   pA  = bf16(c1 + c2 + c3 + c4)                       # rank A rounds
        pB  = bf16(c5 + c6 + c7 + c8)                       # rank B rounds
        out = bf16(pA + pB)                                 # all-reduce rounds
```

Dense rounds once; the bf16 split rounds `ep_size + 1` times. Measured per MoE
block at the production shape (128 experts, top-k 8), the split lands at cosine
`0.999996` and **degrades as you shard more** — `0.999993` at `ep_size 8`, and the
`ep_size 2` vs `ep_size 8` outputs differ by ~4 units. An fp32 all-reduce does not
help: the partial was already rounded to bf16 *inside* `fused_experts`.

**The fix: an fp32 partial-output mode in `fused_experts`.** Each rank emits its
partial in fp32 (skipping the in-kernel bf16 round of the top-k combine), the
partials are summed across the EP group in fp32, and the result is rounded **once**,
exactly reproducing the dense single-rounding:

```text
EP (fp32):  pA = fp32(c1+c2+c3+c4); pB = fp32(c5+c6+c7+c8)  # no rounding
            out = bf16(pA + pB)                             # 1 rounding, == dense
```

Measured at the same shape: **cosine `1.00000000`, max relative error `0`,
bit-exact — and independent of `ep_size`** (the `ep_size 2` and `ep_size 8` outputs
are bit-identical). The mode is opt-in and free for everyone else: `fused_experts`
takes a `partial_output_dtype` that defaults to `None` (no behavior change for any
existing caller); the diffusion EP path passes `torch.float32` and rounds once
after the all-reduce (`LingBotVideoSparseMoeBlock.forward`). Two runs at the same
`ep_size` are of course also bitwise identical.

<details>
<summary>Historical: the bf16 gap, before the fp32 fix</summary>

Three independent checks confirmed the pre-fix gap was rounding, not a logic error:

- The error scales with mantissa width. The identical test in fp16 gives a max
  delta exactly 8× smaller than bf16; fp16 carries 3 more mantissa bits.
- At `top_k = 2` EP is **bit-exact**, because srt combines two slots with a plain
  `torch.add` of already-bf16 rows — a form EP reproduces exactly. The divergence
  appears precisely when srt switches to the fp32-accumulating `moe_sum_reduce`
  at `top_k > 2`.
- At `ep_size = 1` the path is bit-identical to the pre-EP implementation.

**Why one ulp becomes a visibly different video.** 0.94 ulp per block compounded
over 48 blocks predicts a 2.5% perturbation after a single DiT forward. Measured
at one denoise step: 2.17%, PSNR 31.0 dB. Over 12 steps a diffusion sampler
amplifies that chaotically into a different — equally valid — draw: PSNR 13.8 dB,
cosine 0.968, same scene and prompt adherence.

For context, the same comparison across other configuration changes:

| Change (12 steps) | Cosine vs dense non-FSDP baseline |
| --- | --- |
| Enable EP (`ep_size` 2) | 0.968 |
| Enable EP under FSDP (`ep_size` 1 → 2) | 0.934 |
| Enable FSDP, EP off | 0.808 |

Turning on FSDP with EP disabled perturbs the sample *more* than turning on EP.
Sample dependence on reduction order is a pre-existing property of this bf16
pipeline, not something EP introduces.

Reproducibility is preserved *within* a configuration: two runs at the same
`ep_size` are bitwise identical, as are two runs of the dense baseline.

**fp32 in the reduction does not fix this.** Three strategies were measured:

| Reduction strategy | Cosine vs dense |
| --- | --- |
| bf16 partials + bf16 all-reduce (current) | 0.9999959 |
| bf16 partials + fp32 all-reduce | 0.9999959 (no change) |
| per-slot outputs, weights and sum in fp32 | 0.9999949 (slightly worse) |
| dense re-summed from **its own** per-slot outputs | 0.9999949 |

An fp32 all-reduce changes nothing because the partial was already rounded to
bf16 *inside* `fused_experts`. And reconstructing dense from dense's own
per-expert outputs misses by the same margin — the kernel computes
`bf16(acc * w)` while any external reconstruction only has `bf16(acc) * w`.
Closing the gap required an fp32 partial-output mode inside srt's
`fused_experts` — which is exactly what the production path now uses (above).

</details>

## Implementation notes

The pieces, all in `python/sglang/multimodal_gen/`:

- **`runtime/layers/moe.py`** — `resolve_moe_expert_parallel()` derives the
  contiguous shard (`num_local_experts`, `local_expert_start`) from the TP group.
  `LingBotVideoGroupedExperts` then allocates only the local experts.
- **Non-local expert filtering** — `to_local_expert_ids()` rebases global expert
  ids into the rank's local range and maps everything else to `-1`. Setting
  `num_local_experts != num_experts` in `MoeRunnerConfig` flips on srt's
  `filter_expert`, and the Triton kernels write hard zeros for filtered blocks
  *before* applying the routing weight, so a non-local expert contributes
  exactly `0`.
- **The all-reduce** — `LingBotVideoSparseMoeBlock.forward` all-reduces the expert
  output over the TP group. This must happen **before** `shared_experts` is
  added: the shared-expert output is replicated on every rank, so summing it too
  would scale it by `ep_size`.
- **Load-time sharding** — `pack_expert_weights()` packs `w1`+`w3` into
  `w13_weight` and slices both it and `w2` on dim 0 to the rank's expert range.
  The router stays whole and replicated, which is what keeps routing decisions
  identical across ranks.
- **FSDP exclusion** — expert weights are handed to FSDP2 as `ignored_params` via
  the model's `_fsdp_ignored_param_conditions`. EP already owns them, and FSDP's
  all-gather assumes every rank holds a shard of the *same* tensor.

### The `-1` sentinel is mandatory

Non-local experts must be marked with exactly `-1`. This is not a free choice:

- `moe_align_block_size` shifts expert ids by `+1` into an `(E + 1)`-entry
  histogram, so `-1` lands in a dedicated pad bucket and its blocks are labelled
  `-1` for the GEMMs to skip.
- An id equal to `num_local_experts` (a tempting "one past the end" sentinel)
  writes past the shared-memory histogram and can later index `w1[E]` — an
  out-of-bounds weight read, i.e. silent corruption.

`-1` is also srt's own repo-wide sentinel, used by the standard token dispatcher
and honored by the Triton and DeepGEMM runners.

### Guarded kernel hazards

Two srt Triton MoE paths mishandle the filtered-block zero-store, and both are
reachable *only* when EP is on (`filter_expert = True`). Neither fires on the
default configuration, so the MoE block fails loudly rather than silently
corrupting if either is ever enabled:

- `--enable-fused-moe-sum-all-reduce` with `top_k > 2` points the store at the
  combined output while the zero-store still indexes rows by `token * topk`,
  writing out of bounds.
- A tuned `*_down.json` carrying `USE_TMA` makes the up-GEMM output
  expert-sorted while the zero-store keeps unsorted row indices.

### Double-sharding guard

If expert weights were both EP-sharded and FSDP-sharded, FSDP's all-gather would
splice experts from different ranks together — a silent wrong answer, not a
crash. Two guards cover this: the loader raises if an
`_fsdp_ignored_param_conditions` predicate matches *no* parameter (a stale name
pattern would otherwise look identical to "no exclusions requested"), and it
raises again if any matched parameter comes back as a `DTensor` after sharding.

A healthy run logs the exclusion, e.g. for 48 blocks × 2 expert tensors:

```text
Excluding 96 parameters from FSDP sharding in LingBotVideoTransformer3DModel
```

### Router-replication guard

Summing per-rank partial outputs only reconstructs the dense result if every rank
routed each token to the *same* experts. That holds because the router is
replicated and its input is TP-identical — but a violation is silent: the ranks
would compute disjoint halves of two *different* routings, sum them, and produce
a plausible but wrong result. Observed signature when this happens: per-block
cosine against dense drops to ~0.887, versus 0.99999 when healthy.

On the first EP forward each block all-gathers a checksum of its router weights
across the group and raises if they disagree. It runs once per block, and the
end-to-end output is bitwise unchanged with the guard in place.

## Verifying a change to EP

With the fp32 partial-output mode, EP is **bit-exact to dense**, so parity *is* a
usable gate:

1. **Per-operator bit-exactness.** Compare `fused_experts` run densely against the
   fp32 partial-output summed per-rank partials at the production shape (128
   experts, top-k 8). Expect `rtol=0, atol=0` at every `ep_size`. Covered by
   `test_expert_parallel_fp32_partial_is_bit_exact_at_production_top_k` in
   `test/unit/test_lingbot_video_moe.py`.
2. **Determinism / ep-invariance.** Two runs at the same `ep_size`, and runs at
   different `ep_size`, must be bitwise identical.
3. **Memory.** Per-rank expert VRAM should drop by about `1 / ep_size` (measured
   29 GB/rank at `ep_size 2` vs 56 GB dense on the 30B model).
4. **End-to-end.** With the fp32 path the decoded frames match the dense baseline;
   final-frame parity is now a valid check, not just a coherence sanity check.

<Note>
The bf16 partial path (`partial_output_dtype=None`) is *not* bit-exact at
`top_k = 8` — it is ~1 ulp off and drifts with `ep_size`. The tests keep a
`top_k = 2` bit-exact case and a `top_k = 8` ~1-ulp case documenting that legacy
behavior; do not generalize the `top_k = 2` `rtol=0, atol=0` assertion to the bf16
`top_k = 8` path. The production path uses fp32 partials and is bit-exact.
</Note>
